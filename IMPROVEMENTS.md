# Improvement Ideas

A living backlog of concrete, scoped improvements for the Qwixx project,
gathered from a survey of the current codebase (see `CLAUDE.md` for
architecture background). Each row has the idea, why it matters, a
lightweight implementation plan intended as a starting brief for Claude to
pick up and build (not a full spec), and a status column to track
progress over time.

**Status values:** `Not started` · `In progress` · `Done`

When an item is completed, update its Status cell in the same PR that
completes the work (or a quick follow-up) so this stays accurate.

| # | Idea | Why | Implementation plan | Status |
|---|------|-----|----------------------|--------|
| 1 | **Gate deploys on tests, typecheck, and build** — add a CI step that runs `npm test`, `npm run typecheck`, and `npm run build` on every push/PR, and make the Azure auto-deploy workflow depend on it passing. | `.github/workflows/qwixx-AutoDeployTrigger-*.yml` triggers on every push to `master` (`paths: **`) and goes straight to `azure/container-apps-deploy-action`. Nothing runs the existing test suites, `tsc --noEmit`, or a full build first — a broken build or a known regression could still deploy to production. Highest-leverage, lowest-risk item since all checks already exist as npm scripts. | Add a new workflow (e.g. `.github/workflows/ci.yml`) on `push`/`pull_request` running `npm ci`, `npm run typecheck`, `npm test`, `npm run build`.<br>Make `qwixx-AutoDeployTrigger-*.yml` require it to succeed first (`workflow_run` trigger, or add the same steps directly before deploy).<br>Verify with a deliberately broken test, then revert. | Done |
| 2 | **Add ESLint + Prettier** — shared ESLint config (TS + React rules) and Prettier, with a `lint` script per workspace and at the root, wired into CI. | No `.eslintrc*`/`eslint.config*`/`.prettierrc*` anywhere and no `lint` script in any `package.json` — despite `index.ts` and `store/sqlite.ts` carrying `eslint-disable-next-line no-console` comments referencing a linter that doesn't exist. Codebase is otherwise disciplined, so config mostly locks in existing conventions. | Add `eslint`, `typescript-eslint`, `eslint-plugin-react-hooks` (client), `prettier` as root devDependencies.<br>Add root `eslint.config.js` (flat config) with base TS ruleset + client React-hooks override.<br>Add `.prettierrc` and `lint`/`format` scripts at root.<br>Fix violations file-by-file rather than blanket-disabling.<br>Add `lint` to the CI workflow from item 1. | Not started |
| 3 | **Catch client/server protocol drift automatically** — guard against `packages/server/src/protocol.ts` and `packages/client/src/net/protocol.ts` silently diverging. | CLAUDE.md already flags this: the server's zod-validated protocol and the client's manually mirrored plain-TS protocol are independent files with no build-time sync check. A shape change on only one side is a silent runtime bug, not a compile error. | **Lightweight (do first):** add a test that imports both protocol modules' message-type name lists and asserts the sets match; note in the failure message that field-level drift still needs manual review.<br>**Bigger lift (separate follow-up):** extract zod schemas into a shared `packages/protocol` workspace; have the client derive types via `z.infer` instead of hand-mirroring. | Done |
| 4 | **Rate-limit WebSocket messages per connection** — per-connection throttling on inbound WS messages in `packages/server/src/ws.ts`. | `ws.ts`'s `ws.on("message", ...)` handler has no throttling — a misbehaving client can send unlimited `roll_dice`/`submit_white`/etc., each potentially triggering a full table-state re-broadcast. Given the single-instance architecture, this is a real availability risk. | Add a small per-connection counter (e.g. max N messages per rolling 1s window; timestamp-array or token-bucket, no new dependency).<br>On exceeding the limit, drop the message (optionally send a `rate_limited` message) rather than closing the connection.<br>Add a server test bursting messages from one `TestClient` and asserting excess are ignored while the connection stays open. | Not started |
| 5 | **Stand up a client test suite, starting with `legalMoves.ts`** — add Vitest + React Testing Library to `packages/client`. | The client has zero tests: no `test` script, no test framework in devDependencies, no `*.test.*` files. `legalMoves.ts` (wire-format → engine-shape adapter) is exactly the kind of translation layer that silently breaks on shape changes, currently with no safety net despite the engine/server being well-tested. | Add `vitest`, `@testing-library/react`, `@testing-library/jest-dom`, `jsdom` as client devDependencies; add `test` script + `vitest.config.ts`.<br>Write `net/legalMoves.test.ts` covering: no locks, a locked row, and a white sum with no legal moves anywhere.<br>Write one `ScoreSheet.tsx` component test for illegal-vs-legal cell clicks.<br>Add the client `test` script to CI. | Not started |
| 6 | **Spectator mode** — let a client join a table as a read-only observer once all seats are full. | `registry.ts`'s `joinTable` only supports seated players and rejects with `"Table is full"` otherwise — no way to watch a friend's game. The architecture already broadcasts one identical public snapshot to everyone (no hidden info), making spectators structurally cheap. | Server: in `registry.ts`, when no seat is open, attach the connection as a spectator reusing the existing broadcast path, skipping seat assignment.<br>Protocol: add a `role: "player" \| "spectator"` field to join/joined messages in both `protocol.ts` files (see item 3).<br>Client: `Lobby.tsx` offers "Watch" on table-full; `Table.tsx` hides action controls when spectating.<br>Server test: 5th `TestClient` on a 4-seat table gets spectator status + read-only snapshots. | Not started |
| 7 | **In-game text chat** — a simple chat panel scoped to a table, broadcast to everyone connected. | No chat message type in either protocol file and no chat UI anywhere — repo-wide grep for "chat" returns nothing. Notable gap for a social multiplayer game; existing `EventLog.tsx` and broadcast infra make it cheap to add. | Protocol: add `chat_message` (client→server, length-capped) and `chat_broadcast` (server→client) to both `protocol.ts` files.<br>Server: validate and broadcast in `table.ts`/`ws.ts`; no persistence needed initially.<br>Client: `ChatPanel.tsx` (input + scrollback) wired into `Table.tsx` near `EventLog`; extend `socket.ts`'s `ClientState`.<br>Reuse item 4's rate limiter, or add a chat-specific cap. | Not started |
| 8 | **Game history / stats page** — surface finished-game results that are already persisted but currently invisible. | `SqliteStore` already writes `results_json` per finished table, but there's no API route or client screen to browse it — results are visible only transiently in `GameOver.tsx`. Purely a read-path feature; the data model work is done. | Server: add `GET /api/tables/:id/history` reading from `SqliteStore`; keep scope per-table (no cross-game player stats yet — no stable player identity model exists).<br>Client: "View past games" link from `GameOver.tsx` or a standalone route rendering stored final scores. | Not started |
| 9 | **Accessibility pass on the score sheet and turn feedback** — descriptive `aria-label`s on score-sheet cells and an `aria-live` region for turn/phase changes. | Only 7 `aria-*`/`role` attributes exist across the whole client. `ScoreSheet.tsx` uses real `<button>`s (good) but cells have no label describing the action, and there's no live region — phase transitions and dice rolls are invisible to non-visual users. | Add `aria-label`/`aria-pressed`/`aria-disabled` to score-sheet cell buttons.<br>Add a visually-hidden `aria-live="polite"` region (e.g. in `Table.tsx`/`TurnBar.tsx`) announcing phase changes.<br>Add `Escape`-to-close on `GameOver.tsx`'s modal.<br>Spot-check with a screen reader through one full turn cycle. | Not started |
| 10 | **Structured logging via Fastify's pino instance** — replace ad-hoc `console.error`/`console.warn` with the app's existing pino logger. | `app.ts` enables Fastify's `logger: true` pino instance, but `index.ts` and `store/sqlite.ts` use raw `console.*` (each with an `eslint-disable-next-line no-console` pointing at a linter that doesn't exist — see item 2), so app errors and SQLite fallback warnings bypass structured logging entirely. | Thread the Fastify instance's `.log` (or a shared logger) into `index.ts` and `store/sqlite.ts` in place of `console.*`.<br>If `store/sqlite.ts` lacks easy access to the Fastify instance, export a small shared `pino` instance from a new `logger.ts` instead.<br>Drop the now-unneeded `eslint-disable` comments once item 2 lands (or enforce `no-console` at that point). | Not started |
| 11 | **Persistent, dismissible error toasts** — render `lastError`/`errorSeq` as a dismissible toast/banner. | `socket.ts`'s `ClientState` tracks `lastError` and an `errorSeq` counter, but it's unclear from a codebase pass whether this renders persistently or just flashes. No toast/snackbar system exists anywhere in the client; a swallowed or easy-to-miss error is a poor experience in real-time multiplayer. | First, trace where `lastError`/`errorSeq` are currently consumed to confirm this is a real gap before building anything.<br>If it is: add a `Toast.tsx` keyed by `errorSeq` (so repeats re-trigger), mounted near `App.tsx`'s root, auto-dismissing with a manual close.<br>Keep to one active toast at a time — a full queue is over-engineering here. | Not started |

## Not included

A few ideas were considered and deliberately left out of the tracked list
above (not tracked with a status, since they're not planned work):

- **Rule variants / alternate boards** — the engine hardcodes the
  standard Qwixx board (`packages/engine/src/rows.ts`) by design, and
  generalizing it touches scoring, legality, and both protocols. Worth
  revisiting only if there's real demand, since it's a much bigger, more
  invasive change than anything above.
- **Extracting a fully shared protocol package** — listed as the "bigger
  lift" option under item 3 rather than its own row, since the
  lightweight sync-check is the better first move.
